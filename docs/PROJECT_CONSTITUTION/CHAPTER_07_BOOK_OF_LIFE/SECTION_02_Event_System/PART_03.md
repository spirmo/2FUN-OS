CHAPTER_07 — BOOK OF LIFE

SECTION_02 — Event System

PART_03 — ساختار داخلی Event

پس از مشخص شدن مفهوم Event و منابع ایجاد آن، لازم است ساختار استاندارد هر Event تعریف شود.

تمام Eventهای موجود در Book of Life باید از یک قالب مشترک پیروی کنند تا:

- ذخیره‌سازی یکنواخت باشد،
- تحلیل‌ها ساده‌تر شوند،
- و توسعه آینده بدون شکستن سازگاری امکان‌پذیر باشد.

---

اصل بنیادین

هر Event باید ساختاری استاندارد، کامل و مستقل داشته باشد.

---

تعریف Event Structure

«Event Structure مجموعه‌ای از فیلدهای استاندارد است که تمام اطلاعات لازم برای ثبت، ردیابی، تحلیل و بازسازی یک رخداد را در خود نگهداری می‌کند.»

---

هدف این طراحی

این مفهوم برای پاسخ به این پرسش طراحی شده است:

«هر Event دقیقاً چه اطلاعاتی را باید در خود نگهداری کند؟»

---

فیلد اول — Event ID

شناسه یکتای Event.

هیچ دو Event نباید شناسه یکسان داشته باشند.

---

فیلد دوم — Timestamp

زمان دقیق وقوع رخداد.

این فیلد مبنای تمام تحلیل‌های زمانی است.

---

فیلد سوم — Source

منشأ ایجاد Event.

برای مثال:

- User
- Question Engine
- Governance
- Digital Twin
- External System

---

فیلد چهارم — Event Type

نوع رخداد.

برای مثال:

- Login
- Answer Submitted
- Profile Updated
- Recommendation Generated
- Governance Decision

---

فیلد پنجم — Context

زمینه‌ای که رخداد در آن اتفاق افتاده است.

برای مثال:

- Concept مربوط
- Session مربوط
- Lesson مربوط
- مسیر آموزشی

---

فیلد ششم — Payload

اطلاعات اصلی رخداد.

Payload می‌تواند شامل:

- پاسخ کاربر
- مقدار تغییر
- داده‌های محاسبه‌شده
- یا هر اطلاعات اختصاصی Event باشد.

---

فیلد هفتم — Related Entities

ارجاع به موجودیت‌های مرتبط.

برای مثال:

- User ID
- Concept ID
- Question ID
- Session ID

---

فیلد هشتم — Version

نسخه ساختار Event.

این فیلد امکان توسعه آینده را فراهم می‌کند.

---

فیلد نهم — Integrity Information

اطلاعات لازم برای بررسی صحت و یکپارچگی Event.

برای مثال:

- Hash
- Signature
- Validation Status

---

ویژگی کلیدی

هر Event باید به‌تنهایی قابل تفسیر باشد.

یعنی بدون وابستگی به Eventهای دیگر نیز اطلاعات پایه خود را حفظ کند.

---

ارتباط با Timeline

Timeline تنها ترتیب Eventها را نگهداری می‌کند.

اما ساختار داخلی هر Event مستقل باقی می‌ماند.

---

مزایای این طراحی

این معماری باعث می‌شود:

- تحلیل‌ها استاندارد شوند.
- داده‌ها قابل حمل باشند.
- نسخه‌بندی آسان گردد.
- توسعه آینده بدون شکستن سازگاری انجام شود.

---

نگاه فلسفی

در TANDIL:

هر لحظه از زندگی انسان،

باید به‌اندازه‌ای کامل ثبت شود که اگر تمام لحظه‌های دیگر حذف شوند،

آن لحظه همچنان قابل فهم باشد.

---

اصل معماری

بر اساس قانون اساسی TANDIL:

هر Event در Book of Life باید دارای ساختاری استاندارد شامل شناسه یکتا، زمان وقوع، منشأ، نوع رخداد، زمینه، داده اصلی، موجودیت‌های مرتبط، نسخه ساختار و اطلاعات یکپارچگی باشد تا هر رخداد به‌صورت مستقل، قابل ردیابی، قابل تحلیل و قابل بازسازی باقی بماند.

این اصل تضمین می‌کند که کوچک‌ترین واحد ثبت‌شده در Book of Life نیز از کیفیت معماری لازم برای تحلیل‌های آینده برخوردار باشد.
